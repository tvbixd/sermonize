The Problem

Sermon notes shouldn't compete with the sermon

Every Sunday, millions of people sit in church trying to simultaneously listen and write. The result is usually incomplete notes, missed context, and lost scripture references. We experienced this firsthand and kept thinking: the phone is sitting right there — why can't it just listen?

✍

Divided attention

Writing notes pulls focus away from the message. You're either listening or transcribing — rarely both.

📖

Lost scripture references

Pastors reference verses quickly. By the time you find the book and chapter, they've moved on to the next point.

📋

Unstructured output

Handwritten notes lack structure. Going back to review a sermon a week later often means deciphering cryptic shorthand.

The Solution

Tap record, get an outline

Scribe captures audio in real-time, transcribes it with Groq's Whisper model, and uses Llama 3.3 to extract a structured outline — complete with sermon points and every scripture reference cited, looked up in your preferred Bible translation.

1

Record

Audio is captured in 30-second chunks and written to disk immediately. Recording works offline, in the background, and survives app crashes.

expo-av · chunked recording
2

Transcribe

Each chunk is uploaded to Groq's Whisper Large v3 Turbo for fast, accurate transcription. The live transcript updates on screen as the sermon progresses.

Groq Whisper API · streaming
3

Outline

Every two chunks, the running transcript is analyzed by Llama 3.3 70B to produce a live outline: title, theme, summary, and key points.

Groq Llama 3.3 70B · JSON mode
4

Scripture lookup

Detected references are matched against API.Bible across 200+ translations. Each verse is displayed as a tappable card alongside the sermon point that cited it.

API.Bible · regex extraction
5

Review & export

The finished sermon is saved locally with tabs for outline, scriptures, and full transcript. Export as PDF or share directly.

expo-print · expo-sharing

Design Decisions

Thoughtful choices, not defaults

Every design decision was guided by one principle: the app should feel like it disappears while recording and resurface with value when the sermon is over.

One-tap recording

No setup, no configuration before a sermon starts. Tap the red circle and you're recording. The Groq key is entered once in settings and remembered. Getting from pocket to recording takes under two seconds.

Progressive disclosure

During recording, only the timer and a minimal transcript are visible. The full outline, scripture cards, and export options appear after you stop. The interface matches the user's current need.

Guided onboarding

A two-step welcome carousel explains the three value props (transcription, outlining, scripture lookup) with subtle animations. The Groq key setup links directly to the console with clear instructions.

Resilience as UX

Rate limits, network loss, and crashes are first-class states — not error screens. The app auto-pauses, vibrates, and presents clear options. Audio is always safe. Drafts auto-save every five minutes.

Color system

A warm dark palette with intentional accent colors: blue for actions, red for recording state, gold for warnings, green for success. Full light and dark mode support that follows system preference.

Engineering

Hard problems, solved

Building a reliable recording app on a mobile phone is deceptively complex. Here are the engineering challenges that shaped the architecture.

Zero data loss recording

Problem

A sermon can run over an hour. If the app crashes, the phone dies, or the user accidentally swipes away, all audio and transcription is lost.

Solution

Audio is split into 30-second chunks and written to disk immediately. An AppState listener flushes the current chunk on background/lock. Drafts auto-save every 5 minutes. On next launch, orphaned audio directories are detected and converted into recoverable drafts.

Real-time rate limit detection

Problem

Groq's free tier has daily transcription limits. A user could record an entire sermon and only discover afterward that transcription stopped working midway through.

Solution

The app parses Groq's 429 response in real time. On the first rate-limit error, recording auto-pauses, the phone vibrates, and a blocking alert offers three options: save now, switch to audio-only mode, or retry. Audio is always preserved for later re-transcription.

Offline-first architecture

Problem

Church buildings often have unreliable connectivity. The app can't depend on a constant internet connection for its core function.

Solution

A connectivity check runs before recording starts. If offline, the app offers audio-only mode. All data is stored locally — no backend dependency. Saved audio can be re-transcribed later from the sermon detail screen when connectivity returns.

Background recording on mobile

Problem

When the user locks their phone or switches apps, the JavaScript thread freezes, but the native audio session keeps recording into the current segment.

Solution

iOS background audio mode is configured in the native entitlements. An AppState listener detects background transitions and seals the current chunk before suspension. When the app returns to foreground, the chunk timer resumes seamlessly.

Reflections

What we learned

Design for failure states first

The most important screens in Scribe aren't the happy path — they're the rate limit alert, the offline prompt, and the orphan recovery flow. Users don't remember a smooth recording, but they'll never forget a lost one.

Bring-your-own-key is a viable model

By having users provide their own Groq API key, Scribe avoids backend costs entirely. The trade-off is onboarding friction, which we mitigated with an in-app setup guide and direct links to the Groq console.

Chunked recording solves everything

Splitting audio into 30-second segments solved crash recovery, memory pressure, upload size limits, and incremental transcription all at once. One architectural decision, four problems eliminated.

Ship with real resilience, not error messages

Early versions showed error toasts when transcription failed. The final version auto-pauses, saves audio, and offers clear next steps. Users don't need to know what went wrong — they need to know their data is safe.
